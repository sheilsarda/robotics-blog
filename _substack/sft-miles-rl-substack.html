SFT, Miles and RL for Robot Policies

Oct 2, 2026 · @Sheil

Summary

On Oct 2, Qi reported the first reinforcement learning (RL) run at Moonlake: GRPO on a RoboCasa drawer-opening task. A binary reward taught the model nothing. A reward on how far the drawer opened rose steadily and gave one successful rollout after two epochs. RL on our own Isaac tasks still needs one action interface and seeded leases, and the team now names training data as the main bottleneck.

  • What exists. Three supervised fine-tuning (SFT) pipelines: Pi0.5 behavior cloning on minted Arena demos (Nick, Jing Yi), Qwen3.8-27B tool-call SFT on YAM teleop data in Miles (Xiaoyuan), and Qwen SFT on GPT-6's successful RoboCasa365 rollouts (Qi), at about $50 per successful trajectory. env_service already serves simulator episodes that end in a 0 or 1 reward.
  • What Miles is. An open-source RL framework (SGLang for generation, Megatron for training). We use it only for SFT so far. Every hook needed to run RL against env_service exists upstream; no trainer patches look necessary.
  • What the literature says. SFT first, then RL with a plain success reward, is the standard recipe. RL gains are largest when the SFT starting point is weak but not zero (for example LIBERO 48.9% to 96.9% from one demo per task). Only one paper (CaP-X) RL-trains an LLM that writes robot code. It used GRPO on a 7B model and transferred to a real arm. Qi's drawer run fits the pattern: the binary reward failed and a continuous reward learned.
  • The main blockers. (1) Incompatible action interfaces: Xiaoyuan's SFT data, env_service and the customized inspect-robot API that Qi now trains with all differ. (2) No per-session seed, so a group of rollouts cannot share a start state. (3) Near-zero baseline success, which starves a binary reward. Qi's drawer run shows a continuous reward gets past it. (4) Training data: a successful GPT-6 rollout costs about $50. (5) The 4-GPU-per-job Slurm limit that already blocks Xiaoyuan's SFT launch.
  • The first step. Agree one action interface, decide which training data to fund under a fixed budget, and measure the fine-tuned model closed-loop. Qi's drawer run already shows GRPO learning from a continuous reward on RoboCasa.

Primer: the terms in one page

A policy maps what the robot sees (camera images, joint angles, an instruction) to what it does next. Every method below is a different way of adjusting the policy's weights.

  • Supervised fine-tuning (SFT), also called behavior cloning (BC). Show the model a recorded demonstration and train it to predict the demonstrator's next action. The loss is how far its prediction is from the recorded one. It needs good demonstrations, and it can only be as good as them.
  • Reinforcement learning (RL). Let the model attempt the task itself (a rollout), score the attempt with a reward, and nudge the weights so high-scoring behavior becomes more likely. It needs no demonstrations, but it needs some successes to learn from.
  • Sparse binary reward. 1 if the task succeeded at the end, 0 otherwise. Simple and hard to game, but it says nothing about which of 200 actions mattered. Working that out is called credit assignment.
  • PPO (proximal policy optimization). The classic RL update. A second network, the critic, estimates how good each state is, and each update is clipped so the policy cannot change too much at once.
  • GRPO (group relative policy optimization). Drops the critic. Run several rollouts from the same start, and score each against the group's average. If every rollout in a group gets the same reward, the group teaches nothing, which is why a near-zero success rate stalls it.
  • Log-probabilities (log-probs). How likely the model thought each token or action was when it produced it. RL updates need them; SFT does not. Our current rollout logs do not save them.
  • Rejection-sampling fine-tuning (RFT). Run many attempts, keep only the successes, and do SFT on those. A cheap halfway house between SFT and RL. Qi's RoboCasa export is this pattern.
  • Distillation. Train a small or general model to copy a stronger one, such as a privileged-state teacher. Our minting pipeline is distillation from scripted teachers.
  • LoRA (low-rank adaptation). Train small add-on matrices instead of all the weights. Much cheaper, and reported to match full fine-tuning for RL, though that evidence is a blog post, not a paper.
  • On-policy vs off-policy. On-policy means the training data was generated by the current weights. Off-policy (stale) data was generated by older weights and needs a correction such as importance sampling.

Miles

Miles is an RL post-training framework from RadixArk, forked from Zhipu's slime. Release v0.1.1 shipped 2026-09-26. We forked it to MoonlakeAI/miles on 2026-09-24 and use it only for SFT so far.

How it works. Two halves, orchestrated by Ray:

  • Generation (rollouts): SGLang, a fast inference server, behind a load balancer called the Miles Router.
  • Training: Megatron-LM by default, which splits a large model across GPUs, or PyTorch FSDP2, which runs the plain HuggingFace model but has no LoRA support.
  • Weight sync: after each update the new weights are pushed to SGLang. Either both share GPUs and take turns (colocated), or they sit on separate GPUs and weights travel by NCCL broadcast, RDMA, or a shared disk. With LoRA only the adapters move.

What it supports.

  • Algorithms: GRPO, GSPO, REINFORCE++, PPO, plus DAPO-style tricks (wider clipping, dropping groups whose rewards are all equal) and on-policy distillation from a teacher model.
  • SFT: a loss flag that skips SGLang entirely. Our fork trains this way.
  • Vision-language models: yes, through a custom generate function (the upstream geo3k_vlm example runs multi-turn GRPO on Qwen3-VL-2B). The simpler text-only agent path (TITO) has no image support yet.
  • Long, multi-turn episodes: a fully asynchronous mode where generation keeps running while training consumes finished groups, with importance-sampling correction for stale samples.

How an environment plugs in. Three layers, each giving more control:

  1. Agent function: talk to an OpenAI-style chat endpoint; Miles records exact tokens and log-probs. Text only.
  2. Generate function: you own the token sequence, the loss mask and the images. This is the layer we need, because every observation is a camera frame.
  3. Rollout function: you also own batching and the data source.

What our fork changed.

  • An SFT data loader (miles/rollout/code_policy_sft.py) that renders each example through the Qwen processor and checks the prompt is an exact prefix of the full sequence. Only the final assistant turn gets gradient.
  • A launcher for Qwen3.8-27B in LoRA (rank 64) or full mode, defaulting to batch 64 on 2-way tensor parallel.
  • Fixes for FlashAttention 4 on GB300 (a backward-pass bug on the vision tower, and a recompile-on-every-call bug).
  • Resharding a LoRA run onto more GPUs mid-training, held-out validation, and an image-ablation check.

Validation so far. On Qi's branch the RGB-D tool-call SFT finished, and offline it beats the base model: lower held-out loss (0.944 vs 1.055), correct tool 64/64, and 31/31 vs 16/31 chunks accepted by inverse kinematics. Two warnings: the predicted motion is a median 6% of the reference (the model mostly predicts standing still), and blanking the images barely changes the action loss (it may not be looking). Nothing has run closed-loop in a simulator, and SGLang has never been in the loop.

Literature

The published record says: do SFT first, add RL with a plain success reward, and expect the biggest gains when SFT alone gets you partway. Gains that come from RL in simulation only partly survive the move to a real robot. Numbers below were checked against the arXiv abstract or full text unless marked unverified.

SFT of vision-language-action models (VLAs). A VLA is a pretrained vision-language model adapted to output robot actions.

  • The fine-tuning recipe matters as much as the base model. OpenVLA-OFT took LIBERO from 76.5% to 97.1% by changing only decoding, action chunking and the loss.
  • π0, π0.5, GR00T N1 and MolmoAct2 all pretrain broadly, then fine-tune on curated teleop data. MolmoAct2 used 720 hours of bimanual YAM teleop, our robot.
  • Machine-generated demos help most when mixed with real data. Sim-and-Real Co-Training reports +38% average real-world success from adding sim data. Sim-only zero-shot transfer is shown for grasping (GraspVLA) and one assembly task (SkillGen).
  • RLDG distills small RL experts into a generalist and beats human teleop data by up to 40%, because the experts' actions are cleaner. This is the closest published analogue to our scripted-teacher minting.

RL on top of a VLA.

Paper links: SimpleVLA-RL, πRL, RL4VLA, RIPT-VLA, π*0.6 / RECAP, ConRFT, Real-Time EXPO-FT.

Two patterns. First, GRPO works when tasks reset to a fixed start so rollouts in a group are comparable; PPO with a critic did better in ManiSkill, where starts vary more. Second, the strongest real-world numbers come from RL run on the real robot, usually with a human stepping in.

LLMs that write code or call tools.

  • Code as Policies and VoxPoser established the idea. EmbodiedBench found frontier models weak at low-level manipulation (best average 28.9%).
  • CaP-X (ICML 2026) is the one paper that RL-trains a code-writing LLM for robots. GRPO on Qwen2.5-Coder-7B over privileged-state APIs: Cube Lift 25% to 80%, Spill Wipe 30% to 93% in sim. On a real robot, 84% (Lift) and 76% (Stack) against human-written code at 92% and 84%. The sim-to-real gap is small because what transfers is code over APIs.
  • Agentic RL outside robotics shows the same recipe working on long multi-turn tasks: SWE-RL reached 41.0% on SWE-bench Verified, SkyRL took a 32B agent from 24.4% to 39.4% (2511.16108). RAGEN names the main failure: reward variance collapses and training stalls.
  • Endless Terminals warns that big gains on generated tasks (10.7% to 53.3%) can shrink to almost nothing on a human-curated benchmark (1.1% to 6.7%).

Recipes.

  • SFT then RL is near universal. SFT Memorizes, RL Generalizes found RL generalizes better, but SFT is still needed first to fix the output format.
  • Rejection-sampling fine-tuning is the cheap first step (Yuan et al.: GSM8K 35.9% to 49.3%).
  • Distilling a strong model beat running RL directly on a 32B model in DeepSeek-R1 (72.6% vs 47.0% on AIME).
  • LoRA reportedly matches full fine-tuning for RL even at rank 1 (Schulman, blog, not peer reviewed).

Unverified: iRe-VLA and PA-RL numbers, the size of RL4VLA's out-of-distribution gain, and MolmoAct2's "37x faster" claim. Several 2026 papers were checked from abstracts only.

Path to RL

The shortest route is RL on the Qwen3.8-27B tool-calling policy, using Miles as the trainer and env_service as the environment. Miles needs no patches; the work is on our side, in this order.

  1. Agree one action interface. This blocks everything else. Xiaoyuan's data uses move_ee_chunk (two arms, up to 16 goals per call, arm-base frame). Qi's uses move_eef and give_up (one Panda arm). env_service speaks robot_tools.v1 (move_tool, one arm per call, world frame, 10 s cap). A model trained on one cannot act in another. Either add move_ee_chunk to the env_service YAM adapter or regenerate the SFT data in move_tool terms. Camera order, state fields and prompt template must match exactly. Qi now trains with a customized inspect-robot API in place of move_eef and give_up: looser movement limits, no done or give_up tool, and a bash-only agent (miniswe) that can send several calls in one turn. Xiaoyuan is reworking it to need fewer tool calls, after the first SFT checkpoint learned small, correct moves that did nothing for the task. That makes it the leading candidate.
  2. Get a baseline. Launch the LoRA SFT once the 4-GPU Slurm limit is lifted, then run it closed-loop through agent_rollout.py on a fixed set of seeds. Today no model has a committed closed-loop success rate.
  3. Add a seed to the lease. POST /v1/sessions takes only a task id, and the seed is fixed per slot. GRPO needs several rollouts from the same start, so the lease needs a seed field. The slot restart (about 90 s) is the per-episode overhead to plan around.
  4. Write a Miles generate function against env_service. Lease a session, run the multi-turn loop on Miles' SGLang, append each tool result and its camera frames as a no-gradient turn, save token ids and log-probs, then call /finish for the reward. The env_service client must become async, and an abort hook must release every live session.
  5. Start with rejection sampling. Keep successful rollouts and run SFT on them, reusing Qi's export. It needs no log-probs and tests the whole loop. GPT-6 rollouts cost Qi about $50 per success, so the team is moving to cheaper sources: teleop data rewritten as coding trajectories, and Qwen3.8 max rollouts, whose logits also allow distillation into the smaller model. Rewritten teleop data brings its own problems: long runs of digits the small model cannot predict, and a distribution unlike GPT-6's, which makes the two sources hard to mix.
  6. Switch to GRPO once baseline success is clearly above zero. Drop groups whose rewards are all equal, drop infrastructure failures instead of scoring them 0, and use fully async training because episodes take minutes. Qi's drawer run is the first evidence for this step: starting from the SFT model, GRPO with a binary reward did not learn, while a reward on how far the drawer opened rose and reached one success after two epochs.

Risks and open questions.

  • Context length. Three cameras at about 256 tokens per image over 60 turns is about 46k image tokens per episode. Keeping every frame breaks memory; dropping old frames breaks the single-sequence sample RL needs. One option is one training sample per turn, carrying the episode reward; whether Miles normalizes those groups correctly is unverified.
  • Data budget. Qi puts one successful GPT-6 rollout at about $50, close to the cost of building a small environment, and names data scarcity as the biggest bottleneck. With a fixed budget, the team has to choose which data to generate first: better teleop rewrites, Qwen3.8 max rollouts, or fewer tool calls per episode through the robot API.
  • Throughput (estimate, not measured). At 5 to 7 s per command and about 70 calls, one episode is about 10 minutes, or about 24 episodes per simulator GPU-hour. One GRPO step of 64 prompts times 8 rollouts would take about 20 simulator GPU-hours plus inference GPUs. Running many episodes per Isaac process, Modal bursts and fewer, longer tool calls all help.
  • SGLang has never served our model. Multimodal Qwen3.8-27B in SGLang, and syncing LoRA weights into it, is untested.
  • Compute quota. RL needs trainer, inference and simulator GPUs at the same time, and SFT is already blocked on a 4-GPU limit.
  • Alternative route. RL on Pi0.5 in batched Arena already has a fast worker (38.9 environment-steps per second per GPU, about $0.07 per 90 s episode), but needs an RL method for flow-matching policies such as πRL. Nothing like that exists in the repo.
